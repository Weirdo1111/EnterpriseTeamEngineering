# 智慧医养大数据公共服务平台医生服务系统：个人工作报告

**工作方向：临床 AI 助手、RAG 知识库、医嘱安全核查及相关后端集成**  
**项目性质：非商业课程设计**  
**报告日期：2026 年 9 月 28 日**

## 一、个人职责与工作目标

在本项目中，我主要承担临床 AI 助手的后端与算法集成工作，围绕医生接诊后的信息整理、知识检索和用药风险提示，完成模型接入、数据处理、业务接口、安全控制与量化评测。

我的主要目标是减少医生重复整理问诊记录和查找资料的工作量，同时使 AI 输出能够追溯到原始记录或知识来源。系统采用“医生决策、AI 辅助”的定位，不将模型生成内容直接视为诊断或处方依据。

本报告仅统计上述个人负责范围。组员负责的登录注册界面、患者管理、图文问诊业务界面及整体前端设计，不列为我的独立开发成果；与这些模块的接口适配和联调属于我的协作工作。

当前模型配置为 `doubao-seed-2-0-lite-260428` 与 `doubao-embedding-vision-251215`。模型标识通过环境变量配置，密钥不写入报告或业务代码。

架构上，我将文本生成与药物安全判断分开：RAG 负责“检索资料并提供有来源的回答”，DDInter 和规则引擎负责“执行可重复的结构化核查”。药物相互作用不是通过大模型自由猜测得到的。

```text
医生工作台
  -> 身份与角色校验
  -> 临床 AI 业务接口
       -> 病历草稿 / 问诊摘要：原始记录 + 限定模型生成 + 内容校验
       -> 相似病历：模拟病例向量检索 + 相关指南
       -> 医嘱核查：药品解析 + 过敏规则 + DDInter + 可替换药品规则接口
       -> 知识问答：范围过滤 + 混合检索 + 来源聚合 + 方舟生成
  -> 结构化结果、证据来源、未完成项目、审计记录
  -> 医生复核
```

## 三、完成的业务功能

### 1. 病历草稿生成

实现 `POST /api/ai/record-draft`，根据现有问诊记录整理主诉、病史及相关记录，向前端返回可编辑的病历草稿与来源信息。

为了避免将模型推断写成事实，我设置了以下约束：

- 模型生成仅针对服务器内置且逐项匹配的 3 份模拟问诊；不把任意浏览器提交的患者文本发送给模型。
- 对来源引用、数值及已记录的测量信息进行校验；不通过校验或模型异常时退回原始记录的规则化整理。
- 不自动生成处方，不代替医生填写最终诊断。
- 草稿保留医生编辑和复核环节；诊断仍为待评估时，不允许通过病历提交流程。

这一功能完成的是“从问诊信息到可审阅草稿”的辅助流程，不是自动诊断系统，也不是面向真实患者任意文本开放的生成服务。

### 2. 问诊摘要

实现 `POST /api/ai/consultation-summary`，归纳已有问诊内容和后续重点事项，帮助医生快速回顾记录。

摘要与病历草稿使用相同的模拟数据准入及来源校验机制。患者陈述、已记录信息与医生诊断保持区分，避免将未经确认的症状描述改写为确诊结论。

### 3. 相似病历与相关指南

实现 `POST /api/ai/similar-cases`，将医生输入的临床特征进行向量化，在 Synthea 模拟病例中检索相似记录。

检索结果按病例文档聚合，每个病例仅保留得分最高的代表片段，默认最多返回 5 个病例，并单独提供最多 2 条相关指南文档结果。结果包含来源、片段及相似度，明确标记模拟数据身份。

相似度用于排序，不解释为诊断概率。模拟病例用于展示检索与工作流，不作为临床治疗证据。

### 4. Order Safety Check 医嘱安全核查

实现 `POST /api/ai/order-check`，结合拟开药物、患者过敏史和已确认的当前用药清单，输出结构化风险提示。

| 核查环节 | 已实现内容 | 当前边界 |
| --- | --- | --- |
| 药品解析 | 已知成分中英文别名、有限剂量与途径后缀解析；DDInter 通用名映射 | 不猜测未知名称、歧义名称或未解析的复方制剂 |
| 直接过敏 | 对已记录过敏原和已识别成分进行匹配 | 依赖过敏史是否完整、输入是否可靠 |
| 初步类别过敏提示 | 阿莫西林与青霉素过敏的来源关联提示 | 不是完整药理分类或全药物交叉过敏系统 |
| 药物相互作用 | 查询新药与已确认在用药物的 DDInter 药物对 | 未收录药物或药物对显示覆盖缺口，不判定安全 |
| 患者条件提示 | 对记录糖尿病的患者使用 Metoprolol 给出有来源的初步注意事项 | 属于教学辅助提示，不是完整疾病禁忌判断 |
| 剂量与肾功能 | 已建立可替换规则接口，支持途径、日剂量、年龄、eGFR 条件匹配 | 尚未接入经审核的中国药品产品规则，不能宣称完整肾功能剂量评估 |
| 老年用药 | 展示老年用药审查缺口并预留扩展 | 尚未实现完整 Beers 标准核查 |

结果面板返回风险状态、Alerts、Documented Allergies、Checked 和 Not Checked。未完成核查会明确保留，不通过隐藏缺口或把“未发现匹配风险”改成“处方安全”来美化结果。

例如，青霉素过敏患者输入 `Amoxicillin 0.5g oral` 可触发初步青霉素类过敏警告；输入 `Metoprolol` 并在确认的当前用药清单中加入 `Verapamil`，可查到 DDInter 的 `Major` 相互作用记录。后者表示需要重点复核的数据库风险等级，不等同于在所有临床情境下均为绝对禁忌。

## 四、RAG 知识库建设

RAG（Retrieval-Augmented Generation，检索增强生成）的核心是先查找资料，再让模型依据检索证据回答。我完成了从文档导入到带来源回答的处理链路。

### 1. 文档导入与向量化

支持 PPTX、PDF、DOCX，以及符合导入约定的 Synthea FHIR R4 JSON，共 4 类输入。按幻灯片、页面或临床结构组织片段；文档处理配置的最大分块长度为 1400 字符。

导入时保存文档标题、来源位置、发布者、来源链接、许可、模拟数据标记和向量信息。FHIR 处理会排除姓名、地址、联系方式、标识符和精确出生日期，避免把直接身份信息嵌入知识库。

向量存储于 MariaDB，查询时在应用层计算相似度。本项目没有部署专用向量数据库，也没有实现大规模近似最近邻索引，因此不把当前方案描述为经过大规模验证的向量检索平台。

### 2. 混合检索与来源聚合

排序采用语义相似度与词项覆盖混合评分：

```text
Score = 0.85 × cosine_similarity
      + 0.15 × lexical_coverage
      + identifier_boost
```

其中，查询中的编号与来源标题或位置匹配时，可获得 0.2 的编号加分。这是人工设定的排序策略，不是模型置信度或经过训练得到的概率。

对同一文档、同一幻灯片或页面的片段进行来源位置聚合，减少重复结果占用检索名额。知识问答最多返回 8 个排序来源，并附带可定位的片段和引用信息。

### 3. 检索范围隔离

实现 3 类检索范围：

- `project`：项目要求与设计资料。
- `clinical-guideline`：已纳入的老年健康指南。
- `synthetic-patient`：指定的一份模拟病例及相关指南。

指定病例范围必须提供文档 ID，防止回答混入其他患者记录。临床范围内的诊断、处方或具体剂量请求采用拒答策略；证据不足时返回不足说明，不强行生成回答。

### 4. 引用与可追溯性

回答包含 `traceId`、生成时间、检索范围、证据状态、来源和医生复核标记。生成结果缺少有效引用或包含越界引用编号时，降级为检索证据展示。

这里实现的是“引用编号可解析”的校验，尚未实现对每一句话是否被引用材料支持的完整语义验证。

### 5. 限流与导入恢复

针对模型 RPM 限制，默认在连续嵌入请求间设置 1200ms 间隔，并保存持久化导入检查点。导入中断后可以复用已完成的片段向量，减少重复调用；旧版本文档在新版本完成前继续可用，新版本通过事务提交替换。

生成模型返回 HTTP 429 时，知识问答降级为 `retrieval-only`，展示已检索证据。这减少了生成限流对展示流程的影响，但没有消除供应商配额限制；查询向量生成仍依赖嵌入服务，不能宣称所有模型故障下都可用。

## 五、DDInter 数据接入

DDInter 接入采用固定上游 Git 提交版本和 SHA-256 校验，避免数据来源随下载时间变化。接入参考 [OpenMRS DDI 知识库打包项目](https://github.com/pbiondich/openmrs-ddi-knowledge-base)，仅保留本项目使用的通用药名、相互作用药物对、风险等级和机制文本，没有接入其疾病关联表或推断链。

实现上，将药名标准化后映射到唯一 ID，再使用无方向药物对键建立内存 `Map` 索引，保证 A+B 与 B+A 查询一致。歧义名称不进行猜测匹配；`Unknown` 等级和缺失药物对均不视为无风险。

该数据可本地查询，医嘱相互作用核查不必逐次调用大模型。当前没有独立测量这一模块的吞吐量或延迟，因此不报告虚构的 QPS、毫秒级性能指标。

DDInter 数据遵循非商业许可，适用于本项目课程设计范围，不能因为打包项目提供开源代码就认为数据可以任意商用。[DDInter 官方使用条款](https://ddinter.scbdd.com/terms/)

## 七、量化评测与验证

### 1. RAG 检索评测

项目建立了人工编写相关性标签的评测集，包含 29 个范围内检索问题和 1 个范围外问题。答案生成模型不负责给自己的回答打分。

下表来自 2026 年 9 月 27 日保存的评测记录。片段基线与范围过滤、来源聚合方案使用该次评测集进行比较。

| 指标 | 片段检索基线 | 范围过滤与来源聚合 | 变化 |
| --- | ---: | ---: | ---: |
| Precision@5 | 35.2% | 37.9% | +2.7 个百分点 |
| Recall@5 | 87.4% | 93.7% | +6.3 个百分点 |
| Precision@8 | 23.7% | 25.4% | +1.7 个百分点 |
| Recall@8 | 92.5% | 98.3% | +5.8 个百分点 |
| MRR@8 | 92.2% | 96.0% | +3.8 个百分点 |
| nDCG@8 | 87.0% | 92.2% | +5.2 个百分点 |

指标含义：Precision 衡量返回结果中标注相关来源的比例；Recall 衡量标注相关来源被找回的比例；MRR 衡量首个相关结果的排序位置；nDCG 衡量整体排序质量。

同次记录中的检索延迟为 P50 650ms、P95 1532ms，请求错误率为 0%；各检索域的跨域污染率为 0%。这些结果仅适用于当次小规模语料和测试问题，不能据此宣称生产可用性为 100% 或已满足真实医院并发要求。

当前 29 个检索问题共标注 60 个相关来源，每题只有 1 至 3 个。Precision@8 固定按 8 作分母，即使返回不足 8 条也不改变分母，因此该标注集的理论上限为 `60 / (29 × 8) = 25.86%`。实测 25.4% 已接近该上限，不能独立据此判断检索精度差，也不能解读为回答正确率。未标注的补充来源仍不获相关性分数，需要人工复核。

扩展到 12 份文档后未重新执行生成评测，因此该表不能作为扩展语料的生成效果。不同日期的语料与题目发生变化，也不能作为严格控制变量的前后对照。

### 4. 新增检索优化候选方案

新增基于 MiniSearch 的本地全文检索，将关键词排序与语义排序融合，并按相对分数筛选证据，不强制填满 8 个来源。支持中文分词与 NFKC 标准化，保留 `mg` 等短词；不增加向量或生成模型调用。候选必须先通过原有证据分数门槛，弱证据不能仅靠重排变成充分证据。

评测新增 Precision@1、Precision@3、实际返回结果精度、平均返回条数、空结果率和标注理论上限，同时保留原 Precision@8、召回率及全部原始问题标签。返回精度提升必须与召回及遗漏情况一并检查，不能仅通过少返回来源宣称质量提升。

这轮新增 13 项自动化测试，全部通过。因 MariaDB 权限错误，完整 29 题检索评测仍被阻断，尚无可报告的新精度或召回提升。默认仍采用原来源聚合策略，新策略只作为可显式启用的候选，待全量评测及人工复核后再推广。

## 八、工程交付与协作

## 九、当前限制与后续工作

1. **药学规则仍不完整。** 完整交叉过敏、产品级剂量、eGFR 调整和 Beers 标准尚未完成数据接入及审核。当前有可替换接口和部分规则能力，不应写成完整临床核查系统。
2. **真实患者链路尚未开放。** 部分患者数据来自浏览器本地管理，模型生成仅限定模拟问诊。真实患者接入需要服务端数据、权限和数据处理授权。
3. **评测规模有限。** 现有指标用于课程设计工程验证，尚无医生标注的大规模临床测试，也未测得医生工时下降比例或诊疗质量提升。
4. **检索规模能力未验证。** 应用层向量扫描适用于当前小规模知识库；更大语料需要评估索引方案与并发性能。
5. **当前演示环境存在阻塞。** 前端已恢复访问，但本机 MariaDB 拒绝 `localhost` 连接，后端尚未启动成功。修复并完成登录、问答和医嘱核查的端到端验证后，才能确认现场演示链路恢复。

后续优先事项为恢复数据库连接、完成端到端演示检查、扩大人工标注评测集，以及接入经审核的药品产品规则。不会通过删除 Not Checked 或将未收录药物对显示为安全来替代真正的数据建设。

## 十、个人工作总结

我完成了临床 AI 助手相关后端接口与数据处理链路，构建了可追溯的 RAG 知识库，并接入包含 2,283 种药物、295,184 对相互作用的 DDInter 本地索引。通过来源聚合与范围隔离，历史评测中的 Recall@8 达到 98.3%、MRR@8 达到 96.0%；本轮后端回归 61 项测试全部通过，其中 AI 与 RAG 核心测试 48 项。候选全文重排与动态证据选择已经实现，但完整语料的实际提升仍待验证。

我的贡献不仅是调用模型 API，还包括检索排序、数据来源管理、药物知识索引、生成内容校验、限流降级、导入恢复、权限审计衔接和客观评测。项目已形成有来源、有测试、有明确能力边界的课程设计实现，但不将其包装成已验证的临床处方决策系统。
